BUG — DELETE /courses/:courseCode/students/biometrics (BREAKING)
-----------------------------------------------------------------
Symptom:
  Sending { "matricNumber": "190403014" } to the endpoint returned a 422 error:
    {
      "detail": [{ "msg": "Field required", "loc": ["body", "present"] }]

  route only needs matricNumber.

  Affected file: backend/main.py (line 983)
  Broken schema:  schemas.ManualAttendanceRequest  { matricNumber, present }
  Correct schema: schemas.DeleteBiometricsRequest  { matricNumber }

Fix applied:
  1. Added DeleteBiometricsRequest to backend/schemas.py:
       class DeleteBiometricsRequest(BaseModel):
           matricNumber: str

  2. Updated the route in backend/main.py to use the new schema:
       async def delete_course_student_biometrics(
           courseCode: str, req: schemas.DeleteBiometricsRequest
       ):

  After fix: DELETE /courses/CSC101/students/biometrics with
  { "matricNumber": "190403014" } returns 200 ✅

================================================================================

1. backend/requirements.txt
   - Added: bcrypt
     (passlib[bcrypt] was attempted first but has a compatibility bug with
      bcrypt >= 4.0 — "module has no attribute __about__". Switched to using
      the bcrypt library directly instead.)

2. backend/models.py
   - Added passwordHash: Optional[str] = None to the Lecturer model.
     Existing lecturer records without a password hash simply cannot log in
     until updated.

3. backend/schemas.py
   - Added password: str to CreateLecturerRequest (required on creation).
   - Added AdminLoginRequest { password: str }
   - Added LecturerLoginRequest { staffId: str, password: str }

4. backend/.env
   - Added: ADMIN_PASSWORD=password

5. backend/env.py
   - Exposed ADMIN_PASSWORD = os.getenv("ADMIN_PASSWORD", "password")

6. backend/main.py
   - POST /lecturers: now hashes the incoming password with bcrypt before
     storing as passwordHash. Plain password is never persisted.
   - POST /auth/admin/login: compares submitted password against env.ADMIN_PASSWORD.
     Returns { role: "admin" } on success, 401 on failure.
   - POST /auth/lecturer/login: looks up lecturer by staffId, then verifies
     password against stored bcrypt hash.
     Returns { role: "lecturer", staffId, fullName } on success, 401 on failure.
     Uses the same generic error message for both "not found" and "wrong password"
     to avoid user enumeration.

   New helper functions added to main.py (above the routes):
     hash_password(plain: str) -> str
     verify_password(plain: str, hashed: str) -> bool

PROBLEM 1 — [object Object] error on registration form
-------------------------------------------------------
Symptom:
  Submitting the registration form showed "[object Object]" as the error message.

Root cause (two layers):
  1. The backend's POST /courses/:courseCode/register required a "fullName" form
     field but the frontend never sent it. FastAPI returned a 422 validation
     error where "detail" is an array of objects, not a string.
  2. throwOnError() in api.ts did: throw new Error(array) which converts the
     array to the string "[object Object]".

Fixes applied:
  frontend/src/pages/StudentRegistration.tsx
    - Added fullName state variable
    - Added Full Name input field to the form (between Matric Number and Photos)
    - Added fullName.trim() to the submit guard and button disabled check
    - FormData now appends fullName before sending

  frontend/src/lib/api.ts — throwOnError()
    - Now checks if detail is a string, array, or other object
    - If array (FastAPI validation errors): extracts .msg from each item and
      joins them with "; " so the user sees a readable message
    - If object: falls back to JSON.stringify
    - Prevents "[object Object]" from ever appearing as a UI error again


PROBLEM 2 — Misleading placeholder text
----------------------------------------
  Both the registration page and the My Attendance lookup page showed
  "e.g. 19/30CS/01234" as the matric number example. The actual format
  used in the system is all-numeric (e.g. 190403014).

Fixes applied:
  frontend/src/pages/StudentRegistration.tsx — placeholder updated
  frontend/src/pages/StudentPortal.tsx       — placeholder updated
  Both now show: "e.g. 190403014"


PROBLEM 3 — face_recognition not installed (dlib build failure)
----------------------------------------------------------------
Symptom:
  Registration returned: "face recognition service not available on this server"

Root cause:
  dlib (which face_recognition depends on) had no pre-built wheel for
  Python 3.14 and requires Visual C++ build tools to compile from source.
  These were not installed.

Fix applied (local development environment only):
  1. Installed Python 3.11 alongside Python 3.14
  2. Deleted the existing Python 3.14 venv (.venv/)
  3. Created a new venv using Python 3.11:
       py -3.11 -m venv .venv
  4. Installed a pre-built dlib wheel for Python 3.11 Windows directly:
       pip install <pre-built dlib-19.24.1-cp311-cp311-win_amd64.whl>
     (bypasses the need for a C++ compiler entirely)
  5. Ran pip install -r requirements.txt — all packages including
     face_recognition installed successfully
  6. Verified: import face_recognition works correctly
  7. Backend restarted and running on the new venv

  face_recognition is now fully operational locally.


DEPLOYMENT IMPACT OF ALL CHANGES

   ------------------------------------------------
   The local .venv folder is never uploaded to the server. Deployment platforms
   (Render, Railway, Heroku, etc.) install dependencies fresh from
   requirements.txt on their own Linux environment.

   On Linux (which all major cloud hosts use), dlib has pre-built wheels for
   Python 3.9–3.11 AND gcc/g++ is available as a system tool, so dlib compiles
   cleanly without any extra steps. No changes to requirements.txt are needed.

   Action required: None. requirements.txt is unchanged and will work fine
   on the deployment server.
