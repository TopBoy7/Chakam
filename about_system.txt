================================================================================
  1. WHAT IS CHAKAM?
================================================================================

Chakam is a Smart Classroom Occupancy Detection and Attendance Management
System. It combines two independent but connected pipelines:

  1. Real-time occupancy monitoring — using YOLOv8 object detection to count
     how many people are physically present in a classroom at any given moment.

  2. Automatic attendance tracking — using face recognition to identify which
     enrolled students are in an active session and mark them present without
     any manual input from the lecturer.

Both pipelines run from the same image endpoint. When a device (camera) sends
an image to the backend, YOLO runs first to count people and update occupancy.
If there is an active attendance session for that classroom, face recognition
runs next on the same frame to identify and mark students.

The system also provides:
  - Real, server-verified login for every role (student, lecturer, admin) via
    UNILAG email + one-time code — no passwords anywhere.
  - A student self-registration portal (behind login) where students upload
    their own photos and give biometric consent before being enrolled in a
    course they were sent a link to.
  - A student-facing attendance portal (behind login) where a student sees
    only their own attendance record — never anyone else's.
  - Consent management built to comply with Nigeria's Data Protection Act (NDPA)
    2023, including the right to erasure (deleting face data) and the right of
    access (viewing all stored data and consent records).


================================================================================
  2. TECHNOLOGY STACK
================================================================================

BACKEND
  Language:         Python 3.11
  Framework:        FastAPI (async, ASGI)
  Server:           Uvicorn
  Database:         MongoDB Atlas (cloud) via Motor (async driver)
  Image storage:    Cloudinary (annotated images only — never raw photos)
  Object detection: Ultralytics YOLOv8 (yolov8n.pt — nano model)
  Face recognition: face_recognition library + dlib (19.24.1)
  Image processing: OpenCV (cv2) + Pillow (PIL)
  Real-time comms:  WebSocket (built into FastAPI/Starlette)
  Data validation:  Pydantic v2
  Env management:   python-dotenv

FRONTEND
  Language:         TypeScript
  Framework:        React 18
  Build tool:       Vite 5
  UI components:    ShadCN UI (Radix UI primitives + Tailwind CSS)
  Routing:          React Router v6
  HTTP:             Native fetch API (no Axios) — every call goes through a
                    single centralized client (src/lib/api.ts); no component
                    calls fetch directly
  Auth:             JWT bearer token (localStorage). Email + one-time code
                    login for every role, including admin — no password path
                    exists anywhere in the app.
  Real-time:        WebSocket with exponential backoff reconnection,
                    authenticated with a first-message token handshake

DATABASE
  Engine:     MongoDB Atlas (cloud-hosted, TLS)
  Database:   smartclassDB
  Collections:
    - classrooms
    - lecturers
    - courses
    - students
    - enrollments
    - sessions
    - users          (authentication — see section 5)
    - login_codes    (authentication — see section 5)

DEPLOYMENT TOPOLOGY — TWO BACKEND PROCESSES
  Chakam runs as two independent FastAPI processes sharing one MongoDB
  database and one set of support modules (models.py, database.py, env.py,
  send_email.py, auth.py):
    - backend/main.py        "Heavy" backend. Runs YOLO + face_recognition.
                              Reachable directly by camera firmware. Deployed
                              separately from everything else below (its own
                              host — currently needs a manual redeploy step,
                              it is not on the same auto-deploy pipeline as
                              the light backend or frontend).
    - backend/main-light.py  "Light" backend. Deployed on Render. Proxies the
                              image-upload and face-registration endpoints to
                              the heavy backend over HTTP (forwarding the
                              caller's Authorization header so the heavy
                              backend's own role checks still apply), and
                              independently re-implements every other route
                              itself (talking to the same MongoDB directly).
  Both processes register the same route surface and the same auth
  dependencies — a request behaves identically regardless of which one
  handles it, except for the endpoints the light backend forwards.

  The frontend is deployed on Vercel and talks to the light backend
  (VITE_API_BASE_URL / VITE_WS_URL).

  A third, separate app lives in mailer/ — a small Next.js service
  (deployed on Vercel as chakam-mailer) that sends email via Gmail/
  nodemailer. The backend does not send SMTP directly; it POSTs to the
  mailer's /api/send over HTTPS (MAILER_URL, MAILER_SECRET). Both capacity-
  alert emails and login codes go through this. Confirmed working in
  production.

================================================================================
  5. ROLES & PERMISSIONS
================================================================================

Four roles exist: pending, student, lecturer, admin. A user's role lives on
their USER document in MongoDB and is re-read from the database on every
single request (auth.py's get_current_user dependency) — it is never trusted
from the JWT claim. This means a role change, suspension, or promotion by an
admin takes effect on the user's very next request, not after their token
expires.

HOW A ROLE IS ASSIGNED
  On first login, the backend classifies the email address and assigns a
  role automatically, in this order:
    1. Email is in ADMIN_EMAILS (env var)              → role = admin
    2. Email matches an existing Lecturer document      → role = lecturer,
                                                           staffId auto-linked
    3. Email matches the student pattern (matric-based
       local part, e.g. 190403014@live.unilag.edu.ng)  → role = student,
                                                           matricNumber
                                                           derived from the
                                                           local part
    4. Email matches the general staff pattern          → role = pending
       (any other @*.unilag.edu.ng address)
    5. Anything else                                    → rejected, 403
       "must be a UNILAG address"
  A "pending" account has verified their email but has no working role yet
  — they land on /pending-approval and cannot use any protected feature
  until an admin assigns them a role via PUT /admin/users/{email}/role.

PENDING
  Frontend access:  /pending-approval only. ProtectedRoute redirects a
                    pending user to this page from anywhere else.
  Backend access:   Can call GET /auth/me, PATCH /auth/me, POST /auth/logout.
                    Everything else requiring a specific role or "any active
                    role" rejects a pending user.

STUDENT
  Can view:
    - Dashboard, classroom list/detail, course list ("any active role"
      endpoints — GET /classrooms, GET /courses, GET /courses/{code})
    - Their own registration link's course info (GET /register/{token})
    - Their own full attendance record and consent history (GET
      /students/lookup/{matricNumber} — self only; require_self_or_admin
      rejects any matric number that isn't their own)
  Can do:
    - Register their own face for a course they were sent a link to (POST
      /courses/{code}/register) — matricNumber/fullName always come from
      their own JWT, never from the request body, so one student can never
      register as another
    - Delete their own biometric data (DELETE
      /courses/{code}/students/biometrics) — NDPA s.34 right of erasure
  Cannot:
    - View another student's data, another course's enrolled-student list,
      or another course's sessions (assert_course_access requires course
      ownership or admin; a student is neither)
    - Create, edit, or delete classrooms, lecturers, or courses
    - Start/end sessions, capture attendance, or override attendance for
      anyone
    - Reach /attendance/course/:courseId (frontend-restricted to
      lecturer/admin — a student has no legitimate use for it and every
      sub-request the page makes would 403 anyway), /lecturers, /students,
      or /admin/users

LECTURER
  Can view: everything a student can view via "any active role" endpoints,
  plus (for courses they own) the course's enrolled-student list and
  session history.
  Can do:
    - Create a course (POST /courses) — automatically assigned as its
      lecturerId; cannot be overridden by anything in the request
    - For a course where course.lecturerId == their own staffId ("course
      owner or admin", enforced by auth.assert_course_access on the
      backend and mirrored by the frontend's canManage check):
        - Start and end sessions
        - Trigger attendance capture, mark all present
        - Manually toggle a student present/absent, overriding face
          recognition for that student for the rest of the session
        - Enroll/unenroll students
        - View and copy the course's registration link
    - Copy the registration link for ANY course from the /attendance list
      page — copying is a client-side action (no API call), so it isn't
      restricted to owned courses; only the management actions above are.
  Cannot:
    - Manage a course they do not own (403 from the backend even if they
      guess the URL directly — the frontend gate is a convenience, not the
      real enforcement)
    - Rename a course or reassign its lecturer (PUT /courses/{code} is
      admin-only, even for the lecturer's own course)
    - Delete any course, classroom, or lecturer
    - Reach /lecturers, /students, /admin/users, or /my-attendance
      (student-only)

ADMIN
  Full access to every endpoint and every page. Specifically, beyond what
  a lecturer can do:
    - Create/edit/delete classrooms and lecturer profiles
    - Rename any course and (re)assign its lecturer via the Edit Course
      dialog on the course detail page — the lecturer picker there only
      renders once at least one Lecturer profile exists (added via the
      Lecturers page); if none exist yet it shows a message pointing to
      that page instead of silently disappearing
    - Manage sessions/enrollment/attendance for ANY course, regardless of
      lecturerId (assert_course_access always passes for role == "admin")
    - Delete any course
    - Look up any student's attendance record by any matric number
      (require_self_or_admin passes any matric for an admin)
    - Approve pending accounts and assign roles/staffId (PUT
      /admin/users/{email}/role), suspend/reactivate accounts (PUT
      /admin/users/{email}/status)
    - Cannot demote their own account away from admin — a safety check in
      assign_role rejects it, so an admin can never accidentally lock
      themselves out

CAMERA / FIRMWARE (not a user role)
  POST /classrooms/{classId}/image carries no JWT at all — camera firmware
  cannot log in. Its only check is that the request's deviceId field
  matches the classroom's registered deviceId, which is readable from the
  public classrooms list. A shared-secret header for this endpoint was
  built and verified once, then reverted pending a decision with whoever
  owns the ESP32 firmware — see AUTH_CHANGES.md.


================================================================================
  6. THE OCCUPANCY SYSTEM (YOLO)
================================================================================

PURPOSE
  Track how many people are physically present in each classroom at any moment.
  This is separate from attendance — occupancy counts everyone in the room
  (students, lecturers, visitors), not just enrolled students.

HOW IT WORKS

  Step 1 — Image capture
    A physical device (camera/Raspberry Pi/IoT device) sends a POST request to:
      POST /classrooms/{classId}/image
    with a JPEG or PNG image as multipart form data. The request also includes
    a deviceId field which must match the classroom's registered deviceId —
    this ensures only the authorised device for that room can update it.

  Step 2 — Image decoding
    The backend reads the raw bytes and decodes the image with OpenCV
    (cv2.imdecode). If decoding fails the request is rejected with a 400 error.

  Step 3 — YOLO inference
    The YOLOv8 nano model (yolov8n.pt) is loaded lazily on the first request
    and cached in app.state.yolo_model for all subsequent requests. Running it
    on every request would add a multi-second startup cost each time.

    Inference is run in a thread pool executor (asyncio.run_in_executor) so it
    does not block the FastAPI event loop during the CPU-heavy inference.

    Call parameters:
      model.predict(img, imgsz=1920, conf=0.5, iou=0.45)

    - imgsz=1920: processes the image at up to 1920px — higher accuracy for
      distant or small people
    - conf=0.5: detection confidence threshold — boxes below 50% confidence
      are discarded. Raised from an earlier 0.25 after live testing showed a
      single person in frame being counted as 2-4 — the nano model at 0.25
      was counting low-confidence partial detections (limbs, patterned
      background fabric) as extra people. augment=True (test-time
      augmentation, which merges predictions across flipped/scaled passes)
      was removed at the same time — it was compounding the problem by
      letting one person generate several overlapping low-confidence boxes
      that NMS didn't fully collapse. Not yet re-validated against a live
      camera feed beyond that initial fix — if 0.5 still over- or under-
      counts in practice, it may need further tuning.
    - iou=0.45: IoU threshold for non-maximum suppression — removes duplicate
      boxes for the same person

  Step 4 — Person counting
    YOLO returns bounding boxes, each with a class index. Class 0 in the COCO
    dataset is "person". The backend counts how many boxes have class == 0.

    Occupancy is capped at the room's capacity:
      occupancy = min(person_count, classroom.capacity)

    This prevents the displayed occupancy from exceeding the physical maximum
    even if YOLO detects more boxes than seats (e.g. overlapping detections).

  Step 5 — Annotation
    The backend draws two lines of text onto the image:
      - "Occupancy: {count}/{capacity}"
      - Current timestamp in Lagos time (Africa/Lagos timezone)
    Color: light blue (234, 241, 246 in BGR). The annotated frame is then
    JPEG-encoded back to bytes.

  Step 6 — Cloudinary upload
    The annotated image is uploaded to Cloudinary under the folder
    "smart_classrooms/". The old image URL is replaced in the database.
    The previous image is deleted from Cloudinary at the same time to avoid
    accumulating orphaned files.

  Step 7 — Database update
    The classroom document is updated with:
      occupancy: new_count
      latestImage: new_cloudinary_url
      updated_at: now

  Step 8 — WebSocket broadcast
    The backend sends a "classroom_image_update" event over WebSocket to all
    connected frontend clients. The event payload includes the full updated
    classroom document. Every browser viewing the Dashboard immediately sees
    the new occupancy number and the new annotated image without refreshing.

PERFORMANCE
  The endpoint returns timing metrics for every request:
    decode_ms           Image decode time (typically 15–30ms)
    inference_ms        YOLO inference time (typically 200–500ms)
    face_recognition_ms FR pipeline time (800–1500ms, only when session active)
    cloudinary_ms       Upload time (300–600ms)
    db_ms               MongoDB write time (10–50ms)
    ws_broadcast_ms     WebSocket broadcast (5–20ms)
    total_ms            End-to-end total


================================================================================
  7. THE ATTENDANCE TRACKING SYSTEM (FACE RECOGNITION)
================================================================================

PURPOSE
  Automatically identify which enrolled students are present in a classroom
  during an active session, and mark their attendance without any manual input.

HOW IT WORKS — STUDENT REGISTRATION

  Before face recognition can identify a student, the student must register
  and upload their face photos. This requires the student to be logged in —
  the link alone is not enough.

  Step 1 — Lecturer or admin creates a course
    When a course is created, the backend automatically generates a short
    registrationToken (see section 4) and stores it. The lecturer (or admin)
    copies the registration link from the course list or course detail page:
      https://{frontend}/register/{token}

  Step 2 — Student opens the link
    If not logged in, ProtectedRoute sends them to
    /login?redirect=/register/{token} first. They request a one-time code
    with their UNILAG email (POST /auth/request-code — works even if no
    account exists yet), enter the 6-digit code (POST /auth/verify-code —
    creates the account on first success if it didn't already exist), and
    if it's a brand-new account, are asked for their full name once. They
    then land back on the original registration link automatically.
    The frontend resolves the token (GET /register/{token}, requires
    student login) and retrieves the course name to display.

  Step 3 — Consent
    The student is presented with three mandatory consent checkboxes:
      1. Biometric consent — I understand photos will be used to create a
         facial recognition template.
      2. Manual alternative acknowledgment — I understand manual attendance
         is available and not consenting carries no academic penalty.
      3. Age declaration — I confirm I am 18+ or have parental consent.
    All three must be checked. The backend validates this server-side —
    the frontend check alone is not trusted.

  Step 4 — Photo upload
    The student uploads 1 to 5 clear front-facing photos. Different angles
    and lighting conditions improve recognition accuracy. The frontend allows
    drag-and-drop and shows previews of all uploaded images.

  Step 5 — Embedding extraction (backend)
    POST /courses/{courseCode}/register (multipart form, requires student
    login — matricNumber and fullName come from the caller's own JWT, never
    from the request, so a student can only ever register their own face)

    For each photo:
      a. The image bytes are loaded using face_recognition.load_image_file()
         which uses PIL internally and always produces an RGB numpy array.
      b. face_recognition.face_encodings(rgb) is called, which:
         - Detects the face location using dlib's HOG face detector
         - Runs the 68-point facial landmark predictor
         - Passes the face chip through dlib's ResNet face encoder
         - Returns a 128-dimensional float vector (the face embedding)
      c. If no face is detected in a photo, a 422 error is returned telling
         the student which photo failed.
      d. The embedding vector is added to the student's embeddings list.

  DATA MINIMISATION (NDPA s.24):
    The uploaded photos are NEVER written to disk.
    The uploaded photos are NEVER uploaded to Cloudinary.
    Only the 128-float embedding vectors are stored in MongoDB.
    The image bytes are discarded immediately after encoding.
    This means a student's face cannot be reconstructed from stored data.

  Step 6 — Student document creation
    The backend creates (or updates) a student document in MongoDB with:
      - Full name and matric number
      - The list of embedding vectors (one per photo)
      - All three consent flags set to True
      - Consent timestamp and version
    An Enrollment record linking the student to the course is also created.

HOW IT WORKS — SESSION AND ATTENDANCE

  Step 1 — Lecturer (course owner) or admin starts a session
    POST /sessions
    Body: { courseCode, classId }

    The backend checks that no other session is currently active for that
    classroom (one classroom, one active session at a time). A new Session
    document is created with status "active". A "session_started" WebSocket
    event is broadcast to all connected clients.

  Step 2 — Device streams images
    The same POST /classrooms/{classId}/image endpoint that handles YOLO
    occupancy also triggers face recognition. After YOLO counts people, the
    backend checks:
      database.get_active_session_by_classId(classId)

    If no active session exists → face recognition is skipped entirely.
    If an active session exists → face recognition pipeline runs.

  Step 3 — Face detection in the live frame
    The current frame (already decoded as a numpy array) is passed to:
      face_recognition.face_locations(rgb)
    This detects the bounding boxes of all faces in the image.

  Step 4 — Embedding extraction from the frame
    face_recognition.face_encodings(rgb, known_face_locations=locs)
    This extracts a 128-float embedding for each detected face in the frame.

  Step 5 — Comparison against enrolled students
    The backend fetches all enrolled students for the active session's course
    from MongoDB, filtering out any student where embeddingsDeleted == True
    (students who withdrew consent are excluded automatically).

    For each face detected in the current frame:
      For each enrolled student:
        distances = face_recognition.face_distance(
            student.embeddings,  # list of up to 5 reference vectors
            detected_embedding   # current frame embedding
        )
        best_distance = min(distances)

      THRESHOLD CHECK: if best_distance < 0.55:
        → Student identified as present
        → database.mark_attendance(sessionId, matricNumber, method="auto")

    The threshold 0.55 was chosen through testing. A lower threshold (e.g.
    0.4) would reduce false positives but miss more genuine matches. A higher
    threshold (e.g. 0.7) accepts more matches but risks false identifications.
    0.55 is a balanced default for controlled classroom environments.

  Step 6 — Mark attendance (idempotent)
    The mark_attendance database function is designed to be safe to call
    multiple times for the same student in the same session:
      - If the student already has an attendance record that was NOT manually
        overridden: update the markedAt timestamp (refresh the detection time).
      - If the student has a manually overridden record: do nothing. The
        lecturer's manual decision is final and face recognition cannot undo it.
      - If the student has no record yet: insert a new AttendanceEntry.
    This means even if the camera sends images every few seconds, the same
    student is not marked multiple times — they are simply re-confirmed.

  Step 7 — Broadcast attendance update
    If any new students were marked in this frame, a "attendance_update"
    WebSocket event is broadcast to all connected clients. The payload includes
    the updated session state and the list of newly marked matric numbers. The
    lecturer's browser updates the attendance list in real-time.

  Step 8 — Manual override (course owner or admin only)
    PUT /sessions/{sessionId}/attendance/{matricNumber}
    Body: { status: "present" | "absent" }

    The lecturer who owns the course (or an admin) can manually set any
    student as present or absent at any time during or after a session:
      - Sets manuallyOverridden: True on the attendance entry, and an
        explicit present: True/False on the SAME entry — both present and
        absent overrides are upserted in place, never removed from the
        attendees array
      - Once manually overridden, face recognition will never modify that
        student's record for the rest of the session

    FIXED (2026-08-28): "mark absent" used to $pull (delete) the attendee's
    entry outright instead of upserting present: False. That left no
    manuallyOverridden lock behind, so the very next auto-recognition frame
    that matched the student's face silently re-marked them present —
    overrides only actually held for the "present" direction, never for
    "absent". AttendanceEntry now has a real `present: bool = True` field
    (models.py); manual_attendance_override (database.py) upserts both
    directions identically; every place that used to treat "member of the
    attendees array" as synonymous with "present" — totalPresent in
    GET /sessions/{id}/attendance, the on-image "Present: N" annotation
    label, the /sessions/{id}/capture stub, and the frontend's
    transformAttendees/transformSession in api.ts — now filters on the
    `present` field instead of array membership. A student sees the same
    status as a read-only indicator — they cannot trigger this action.

  Step 9 — End session (course owner or admin only)
    POST /sessions/{sessionId}/end

    Sets status: "ended" and endedAt: now. Once ended, face recognition on
    subsequent images will no longer mark attendance for this session. The
    attendance record is frozen.

CONSENT WITHDRAWAL (NDPA s.35 — Withdrawal of consent, giving rise to the
                     s.34 right of erasure)
  DELETE /courses/{courseCode}/students/biometrics
  Body: { matricNumber }
  Requires login: the student themself, or an admin.

  Execution:
    - Sets embeddings: [] (clears all stored vectors)
    - Sets embeddingsDeleted: True
    - Sets consentWithdrawnAt: now()
    - The student document is NOT deleted — only biometric data is erased
    - All past attendance records are preserved
    - Future face recognition queries skip this student entirely
    - The student portal will still show their full attendance history


================================================================================
  8. HOW OCCUPANCY AND ATTENDANCE ARE CONNECTED
================================================================================

They share one endpoint, one physical device, and one classroom.

  Single image endpoint:
    POST /classrooms/{classId}/image

    This single endpoint does both jobs from the same image in one request:
      1. Run YOLO → count people → update occupancy
      2. Check for active session → if found, run face recognition → mark attendance

  Shared classroom context:
    Both systems are anchored to a classId. When a camera device sends an
    image, it identifies itself by classId and deviceId. The YOLO result
    updates that classroom's occupancy. The face recognition check looks for
    an active session with that same classId. The two systems do not know about
    each other — they both independently read and write through the classroom
    as a shared anchor.

  One does NOT require the other:
    - Occupancy updates run always, regardless of whether there is an active
      session. A classroom can track occupancy 24/7 with no courses configured.
    - Attendance tracking only runs when a session is active. If no session is
      active, face recognition is completely skipped (no compute wasted).

  They share the same real-time channel:
    Both the occupancy update and the attendance update are broadcast over the
    same WebSocket connection. The frontend listens for two events:
      "classroom_image_update"  → update occupancy + latest image in Dashboard
      "attendance_update"       → update attendance list in CourseDetail page

  Practical classroom flow:
    1. Camera continuously sends images (e.g. every 10-30 seconds)
    2. Dashboard always shows live headcount (occupancy from YOLO)
    3. Before class: lecturer (course owner) or admin starts a session via
       the course detail page
    4. During class: same camera images now also trigger face recognition
    5. Students are marked present automatically as they are detected
    6. Lecturer can monitor the attendance list updating in real-time, and
       trigger a manual "Take Attendance" / "Mark All Present" capture
    7. After class: lecturer ends the session
    8. Occupancy continues updating; attendance is now frozen


================================================================================
  9. FRONTEND ARCHITECTURE
================================================================================

API CLIENT (src/lib/api.ts)
  All HTTP calls go through a single centralized api object. No component
  calls fetch directly. This means the base URL, error handling, and data
  transformation are defined in one place. (This was violated once — a raw
  fetch() in StudentRegistration.tsx that never attached the auth header,
  found and fixed.)

  Error handling (throwOnError):
    FastAPI returns validation errors as an array of objects under "detail".
    A plain new Error(array) would produce "[object Object]". throwOnError
    parses the response body and extracts human-readable messages from both
    string and array detail formats.

  Transform functions:
    Raw MongoDB documents use snake_case or unusual field names. Transform
    functions (transformCourse, transformSession, etc.) normalize them into
    typed TypeScript interfaces that the frontend works with. transformCourse
    includes lecturerId, which the frontend uses to compute course ownership
    (see canManage below).

AUTH CONTEXT (src/contexts/AuthContext.tsx)
  Real server-side authentication (all four phases of auth_design.txt — see
  AUTH_CHANGES.md for the full change log). Every role, including admin, logs
  in with their UNILAG email and a one-time code sent by mail
  (POST /auth/request-code, POST /auth/verify-code); the backend issues a
  JWT, stored in localStorage and sent as an Authorization: Bearer header on
  every request. AuthContext exposes { token, user, loading, isAdmin,
  loginWithToken, logout, refreshUser }. isAdmin is simply
  user?.role === "admin". The user object is never trusted from a cache — it
  is re-fetched from GET /auth/me on every mount.

  There is no password login path anywhere in the app. The old
  VITE_ADMIN_PASSWORD fallback has been fully removed from AuthContext,
  ProtectedRoute, and Home.tsx.

  Role is never trusted from the JWT claim on the backend — auth.py's
  get_current_user dependency re-reads the role from MongoDB on every
  request, so a promotion, suspension, or role change by an admin takes
  effect immediately rather than waiting for the token to expire.

COURSE OWNERSHIP ("canManage") — src/pages/CourseDetail.tsx
  The backend's real permission rule for managing a course is "course owner
  (lecturer whose staffId matches course.lecturerId) or admin" — never just
  "any lecturer". The frontend mirrors this:
    isCourseOwner = user?.role === "lecturer" && !!user.staffId
                    && course?.lecturerId === user.staffId
    canManage = isAdmin || isCourseOwner
  canManage gates: Start Class, End Class, Take Attendance / capture, Mark
  All Present, the manual present/absent toggle (non-managers see the same
  status as a read-only icon instead of a clickable button), and
  Enroll/Unenroll Student. "Edit Course" (rename / reassign lecturer) stays
  admin-only, matching PUT /courses/{code} being admin-only even for the
  course's own lecturer.

WEBSOCKET HOOK (src/hooks/useClassroomWebSocket.ts)
  Manages the WebSocket connection lifecycle:
    - Auto-connects on mount
    - Sends the JWT as the connection's first message
      (JSON.stringify({ token })) — the backend closes any connection that
      hasn't authenticated within 5 seconds, since browsers cannot set
      headers on a WebSocket handshake
    - Sends a ping message every 25 seconds to keep the connection alive
      (prevents proxy/load balancer idle timeout disconnects)
    - On disconnect: reconnects with exponential backoff starting at 1 second,
      doubling each time up to a maximum of 30 seconds — the token is re-sent
      as the first message on every reconnect
    - Cleans up on component unmount

ROUTING (src/App.tsx)
  Public routes (no auth required):
    /                     Home page
    /login                Email + one-time-code login (the only login path)

  Requires being logged in as any active (non-pending) role — redirects to
  /login?redirect=<path> if logged out (returning here after verifying), or
  to /pending-approval if the account has no role assigned yet:
    /dashboard             Classroom overview
    /classroom/:classId    Classroom detail
    /attendance            Course list — "Create Course" shown to lecturer
                           and admin; "Delete" shown to admin only

  Lecturer + admin only (ProtectedRoute allowedRoles={["lecturer","admin"]}):
    /attendance/course/:courseId   Course detail, sessions, attendance,
                                   enrollment. Narrowed from including
                                   "student" because a student has no
                                   legitimate use for this page and every
                                   sub-request it makes (students list,
                                   sessions list) is course-owner-or-admin
                                   gated and would 403 for them anyway —
                                   they now get a clean redirect to
                                   /dashboard instead of a broken error page.

  Student only (ProtectedRoute allowedRoles={["student"]}) — same
  redirect-and-return behaviour. A student can only ever register or view
  their own record, never anyone else's, since the matric number comes from
  the token instead of a typed-in value or URL parameter:
    /register/:token       Student self-registration
    /my-attendance         Student portal — shows the logged-in student's
                           own record automatically, no matric entry.
                           Not shown in the nav to lecturers/admins (it used
                           to be, which just redirected them away when
                           clicked).

  Admin-only (ProtectedRoute allowedRoles={["admin"]}):
    /lecturers             Lecturer management
    /students              Student management
    /admin/users           Approve pending accounts, assign roles

  /pending-approval        Holding screen for a verified account with no
                           role assigned yet.

  NOT routed: /analytics — Analytics.tsx exists in the codebase but has no
  <Route> entry. Considered redundant with the Dashboard's live occupancy
  view; left unrouted rather than wired up.

ENVIRONMENT VARIABLES (frontend/.env)

================================================================================
  11. NDPA COMPLIANCE
================================================================================

The Nigeria Data Protection Act 2023 compliance is built into the system at
the data layer, not bolted on as an afterthought.

  s.24 — Data minimisation
    Uploaded registration photos are processed in memory only. They are never
    written to disk, never stored in the database, and never uploaded to
    Cloudinary. Only the 128-float embedding vectors extracted from the photos
    are stored. A face cannot be reconstructed from an embedding vector — the
    process is mathematically one-way.

  s.31 — Age requirement
    The registration form requires the student to explicitly confirm they are
    18 or older, or have parental/guardian consent. This is validated server-
    side — the backend returns a 422 if ageConsent is not "true".

  s.34 — Rights of a data subject (including access)
    The student portal (GET /students/lookup/{matricNumber}) returns the
    student's complete attendance history, consent timestamp, consent version,
    biometric active status, and consent withdrawal date if applicable, plus
    an identity block (email, role, emailVerifiedAt, lastLoginAt). A student
    may only pass their own matric number; an admin may pass any
    (require_self_or_admin). The email address collected by the auth work is
    personal data under the Act and is included in this same right-of-access
    response.

  s.34 — Right to erasure, with s.35 — Withdrawal of consent
    DELETE /courses/{courseCode}/students/biometrics
    Instantly clears the embeddings array and sets embeddingsDeleted: True.
    Future face recognition queries filter out this student. The student record
    and all attendance history are preserved (non-biometric data). The consent
    withdrawal timestamp is stored for the audit trail.

    This endpoint is exercised as a withdrawal of consent under s.35, which
    triggers erasure of the data that was processed on that consent basis;
    erasure itself — along with access, correction, and restriction — sits
    under s.34 "Rights of a data subject" (the Act bundles all of these as
    subsections of one section, not four separate sections). s.36 is "Right
    to object" and s.38 is "Data portability" — neither is erasure, and both
    were previously miscited in the frontend consent notice as if they were.

    VERIFIED (2026-08-28) against the Act's own Arrangement of Sections
    (cross-checked via lawnigeria.com and corroborating summaries): s.24
    principles/minimisation, s.26 consent, s.30 sensitive/biometric data,
    s.31 children/incapacity, s.34 rights of a data subject (access +
    correction + erasure + restriction), s.35 withdrawal of consent, s.36
    right to object, s.37 automated decision-making, s.38 data portability.
    Every citation in the frontend (StudentRegistration.tsx, StudentPortal.tsx)
    and backend (main.py docstrings) was corrected to match — see section 13.

  s.30(1)(a) / s.26 — Manual alternative, now backed by a real code path
    The system never makes biometric consent compulsory. Every registration
    page explicitly states that a manual attendance alternative is available
    and that not consenting carries no academic penalty. The manualAltConsent
    checkbox confirms the student understood this — and is required for
    registration to proceed, ensuring the student has genuinely read it.

    This claim used to be aspirational only: POST /courses/{code}/enrollments
    required an existing Student document, and the only two endpoints that
    ever create one both required face photos — so a student who declined
    biometric consent could never actually be added to a course roster by a
    lecturer. Fixed 2026-08-28 (see section 13) — enroll_student now creates
    a bare, embeddings-less Student record when the lecturer supplies a
    fullName for an unregistered matric number. This is why "freely given"
    (s.26) consent matters here specifically: a promised opt-out with no
    working system path behind it undercuts the freeness of the consent.

================================================================================
  13. KNOWN LIMITATIONS & NOTES
================================================================================

- Nothing in this session's changes takes effect on the live site until it
  is committed, pushed, and (for the heavy backend specifically) manually
  redeployed — see section 12. Check git status before assuming any fix
  described in this document is actually live.

- The camera image endpoint (POST /classrooms/{classId}/image) has no secret
  or credential beyond the pre-existing deviceId comparison, which is
  discoverable from the public classrooms API. A shared-secret header for
  this endpoint was built, verified, and then reverted — hardware/firmware is
  outside the current maintainer's control and needs a decision with whoever
  owns the ESP32 firmware before this is attempted again.

- face_recognition and dlib are not imported at module level in main.py. The
  server starts and runs normally without them — only the registration and
  image capture endpoints will fail at runtime if they are not installed. This
  allows the backend to run in "occupancy-only" mode on lightweight deployments.

- The student portal (GET /students/lookup/{matricNumber}) returns 404 if the
  student has no ended sessions yet. Students who are registered but have had
  no sessions will see a not-found error rather than an empty results page.

- YOLOv8 nano (yolov8n.pt) is the smallest and fastest YOLO variant. It trades
  some accuracy for speed. Confidence threshold history, now backed by git
  history rather than just prose:
    - 2025-11-27 (first backend commit): conf=0.25, iou=0.45, augment=True —
      all three chosen together and commented deliberately ("sensitive to
      small objects" / "keeps tiny detections" / "improves accuracy
      significantly"). Ran unchanged for ~9 months.
    - 2026-08-19, commit 7321a08d "count fix" (10 days before this session):
      conf raised to 0.5 AND augment=True removed, in the SAME commit. The
      commit's own comment blames a single person reading as 2-4 on BOTH
      together, specifically calling out augment's multi-scale merging as
      the amplifying factor — but neither variable was tested in isolation
      before both were changed at once. This is a confounded fix: it's not
      actually known whether conf, augment, or their interaction was the
      real cause.
    - 2026-08-29 (this session): briefly tried conf=0.4 as a compromise
      between 0.5's confirmed dense-crowd under-count (~20 detected on a
      ~100-person photo, see the "FIRST LIVE FUNCTIONAL TEST RUN" note) and
      0.25's original over-count report — then reverted to conf=0.25,
      augment left OFF, after checking the git history above. Reasoning:
      since the "count fix" commit's own comment points at augment as the
      amplifier, and augment is already off, 0.25-without-augment is a
      genuinely different, untested configuration from whatever the

- Added `--capture` mode to chakam_attendance_test.py (2026-08-29) — for
  collecting REAL frames from the physical device during a live B1/D1
  trial, not substitute photos. The obstacle: upload_image (main.py)

- HARDWARE FINDING (2026-08-30) — the physical ESP32 camera's image quality
  is genuinely limiting results, confirmed by --capture during a real test
  run: significant blur, consistent under-counting even in ordinary rooms
  (not just the earlier dense stock photo — e.g. one real indoor capture
  showed 3-4 people in frame but occupancy read 1), and face recognition
  for attendance only working when the device is held very close to a
  face. Root cause identified from firmware/CameraConfig.h and
  firmware.ino: the device's pin-mapping helper is named
  esp32S3WroomOV5640Pins(), but the camera is constructed with
  SensorModel::OV2640 as the expected/validated sensor — and since the
  device successfully initialises (validateSensorModel() would fail
  camera.begin() otherwise), the physically populated sensor is
  confirmed to actually be an OV2640, a common budget module frequently
  paired with a short, sometimes fixed-focus lens. That lens
  characteristic — sharp close, blurry at any real distance — matches the
  "have to hold it right up to their face" symptom exactly. Actual
  in-use capture settings (setNormalCameraProfile(): FRAMESIZE_SVGA
  800x600, JPEG quality 12) are reasonable for what the sensor can do —
  this is not a software setting quietly crippling image quality, the
  ceiling is the sensor/lens itself. (The separate FRAMESIZE_QVGA/quality
  25 profile in setApStreamCameraProfile() is only for the local AP
  live-preview stream, not the uploads YOLO/face_recognition actually
  process — not the cause.) Not yet checked: whether this specific
  module's lens has a manually-rotatable focus ring (some OV2640 boards
  do) — worth a two-minute physical check before treating this as a hard
  ceiling.

- Added camera_simulator.html at the repo root (2026-08-30) — works
  around the hardware finding above rather than waiting on a lens fix or
  hardware swap. A single self-contained HTML/JS page (no build step, no
  dependencies) that uses the browser's own camera (laptop webcam or,
  better, a phone's camera via a local HTTPS tunnel — phone cameras
  generally have real autofocus the ESP32 module lacks) and POSTs frames
  to the exact same POST /classrooms/{classId}/image endpoint the real
  device uses. This endpoint has no auth dependency and CORS is already
  wide open (allow_origins=["*"] in main.py), so a plain browser fetch()
  works with zero backend changes. Config (API base URL / class_id /
  device_id) is editable in the page and persisted via localStorage.
  Supports one-off capture or an auto-capture loop on a configurable
  interval (default 3s, matching the real device's cadence) — meaning it
  composes with --capture exactly like the real hardware would, just
  with better source image quality. Must be served (e.g. `python -m
  http.server`), not opened as a bare file:// page — getUserMedia
  requires a secure context, which file:// and plain http:// over a LAN
  IP do not satisfy; localhost is fine, a phone needs an HTTPS tunnel
  (e.g. ngrok) to reach a laptop-hosted instance securely.

  fixed by this live run, all encoding-related and all Windows-specific

  default filesystem/locale encoding is already UTF-8):
    1. _images_from_dir only globbed .jpg/.jpeg/.png — two of the

       silently reported "no images" even though real files were sitting

    2. save_results() wrote report.txt, results.json, and summary.csv via

- RESOLVED (2026-08-29) — full registration outage, four separate causes
  stacked on top of each other. Documenting the whole sequence here since
  it's a real multi-layered incident, useful as-is for a report's testing/
  challenges section:

  1. Stale heavy backend code (above) — the pre-existing matricNumber/
     fullName requirement. Fixed by redeploying the heavy backend with
     current code. Verified via GET /openapi.json before and after.

  2. New problem surfaced BY that redeploy: JWT_SECRET mismatch between
     the light backend (Render) and the heavy backend (AWS/DuckDNS) — two
     separate deployments, two separately-configured copies of the same
     secret. Evidence this was NEW, not pre-existing: the earlier failure
     (cause 1) was a 422 on missing form fields, which only happens if the
     token passed the auth check first — meaning the secrets matched
     before the redeploy. Immediately after, the same kind of request
     failed with 401 at the exact point it reached the heavy backend,
     while everything that stayed on the light backend kept working fine.
     That pattern (works on light-only calls, fails instantly the moment a
     request crosses to heavy) is what pointed at the secret specifically,
     not a real token expiry (which would be slow, not instant, and would
     fail everywhere, not just on the one hop). Root cause: the manual
     redeploy process used for the heavy backend evidently didn't carry
     over the original .env — it came back up with a different
     JWT_SECRET than it had five minutes earlier. Fixed by copying the
     light backend's JWT_SECRET value onto the heavy backend and
     restarting it.

  3. Separately found while investigating: the light backend's own
     HEAVY_BACKEND_URL environment variable was pointing at the wrong
     address entirely. Corrected independently of (2).

  4. Even with (1)-(3) fixed, real registration submissions (genuine
     token, genuine photos) still failed — this time with "invalid
     response from analytics server", the light backend's fallback text
     for when it gets back a response it can't parse as JSON. Confirmed
     via direct testing that this is NOT the same failure mode as a
     timeout (a timeout is caught separately and surfaces as a clean 503
     "face recognition service currently unavailable") and NOT a
     connectivity/URL problem (a direct POST to the corrected heavy
     backend URL, with deliberately bad auth, returned a clean, well-
     formed 401 — proving the server itself is reachable and functioning
     for anything that doesn't reach the real face-processing code). That
     leaves the actual face-embedding extraction step (decoding 5 real
     photos through face_recognition/dlib) as the most likely site of the
     failure — either a crash partway through, or a reverse proxy/load
     balancer in front of the heavy backend giving up and returning an
     empty response before that processing finishes. This could not be
     confirmed further without server-side log access, which wasn't
     available during this session.

  RESOLUTION: rather than keep chasing (4) blind, the frontend
  (VITE_API_BASE_URL / VITE_WS_URL on Vercel) was pointed directly at the
  heavy backend, bypassing the light backend's proxy hop for registration
  entirely. Confirmed safe to do — the heavy backend already has
  permissive CORS (allow_origins=["*"] in main.py) and implements the same
  /ws WebSocket handshake as the light backend. Registration now works
  end-to-end; test students have been successfully registered live.

  STANDING CONSEQUENCE: the frontend currently talks to the heavy backend
  for everything, not just registration — a bigger topology change than
  originally intended (see section 2's deployment topology, which assumes
  the frontend talks to the light backend). The specific bug in (4), on
  the light→heavy proxy path, remains unresolved and unexplained. If the
  frontend is ever pointed back at the light backend, registration should
  be re-tested before assuming it still works — the underlying cause
  there was never actually found, only routed around.

  chakam_attendance_test.py's config.json was updated to match —
  api_base_url now also points at chakam-api.duckdns.org, so test results
  reflect the same backend real users are actually hitting.
