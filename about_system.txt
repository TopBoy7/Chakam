================================================================================
  1. WHAT IS CHAKAM?
================================================================================

Chakam is a Smart Classroom Occupancy Detection and Attendance Management
System. It combines two independent but connected pipelines:

  1. Real-time occupancy monitoring — using YOLOv8 object detection to count
     how many people are physically present in a classroom at any given moment.

  2. Automatic attendance tracking — using face recognition to identify which
     enrolled students are in an active session and mark them present without
     any manual input from the lecturer.

Both pipelines run from the same image endpoint. When a device (camera) sends
an image to the backend, YOLO runs first to count people and update occupancy.
If there is an active attendance session for that classroom, face recognition
runs next on the same frame to identify and mark students.

The system also provides:
  - A student self-registration portal where students upload their own photos
    and give biometric consent before being enrolled in a course.
  - A student-facing attendance portal where any student can look up their own
    attendance record using only their matric number.
  - Consent management built to comply with Nigeria's Data Protection Act (NDPA)
    2023, including the right to erasure (deleting face data) and the right of
    access (viewing all stored data and consent records).


================================================================================
  2. TECHNOLOGY STACK
================================================================================

BACKEND
  Language:         Python 3.11
  Framework:        FastAPI (async, ASGI)
  Server:           Uvicorn
  Database:         MongoDB Atlas (cloud) via Motor (async driver)
  Image storage:    Cloudinary (annotated images only — never raw photos)
  Object detection: Ultralytics YOLOv8 (yolov8n.pt — nano model)
  Face recognition: face_recognition library + dlib (19.24.1)
  Image processing: OpenCV (cv2) + Pillow (PIL)
  Real-time comms:  WebSocket (built into FastAPI/Starlette)
  Data validation:  Pydantic v2
  Env management:   python-dotenv

FRONTEND
  Language:         TypeScript
  Framework:        React 18
  Build tool:       Vite 5
  UI components:    ShadCN UI (Radix UI primitives + Tailwind CSS)
  Routing:          React Router v6
  Charts:           Recharts
  HTTP:             Native fetch API (no Axios)
  Auth:             JWT bearer token (localStorage), plus a legacy admin
                    password path kept working in parallel — see section 8.
  Real-time:        WebSocket with exponential backoff reconnection,
                    authenticated with a first-message token handshake

DATABASE
  Engine:     MongoDB Atlas (cloud-hosted, TLS)
  Database:   smartclassDB
  Collections:
    - classrooms
    - lecturers
    - courses
    - students
    - enrollments
    - sessions
    - users          (added for authentication — see section 4)
    - login_codes     (added for authentication — see section 4)

DEPLOYMENT TOPOLOGY — TWO BACKEND PROCESSES
  Chakam actually runs as two independent FastAPI processes sharing one
  MongoDB database and one set of support modules (models.py, database.py,
  env.py, send_email.py, auth.py):
    - backend/main.py        "Heavy" backend. Runs YOLO + face_recognition.
                              Reachable directly by camera firmware.
    - backend/main-light.py  "Light" backend. Proxies the image-upload and
                              face-registration endpoints to the heavy
                              backend over HTTP, and independently
                              re-implements every other route itself (talking
                              to the same MongoDB directly, not through the
                              heavy backend).
  Both processes register the same route surface and the same auth
  dependencies — a request behaves identically regardless of which one
  handles it, except for the three heavy-only endpoints the light backend
  forwards.

  A third, separate app lives in mailer/ — a small Next.js service that
  sends email via Gmail/nodemailer. The backend does not send SMTP directly;
  it POSTs to the mailer's /api/send over HTTPS (MAILER_URL, MAILER_SECRET).
  This is what both capacity-alert emails and login codes go through.

================================================================================
  5. THE OCCUPANCY SYSTEM (YOLO)
================================================================================

PURPOSE
  Track how many people are physically present in each classroom at any moment.
  This is separate from attendance — occupancy counts everyone in the room
  (students, lecturers, visitors), not just enrolled students.

HOW IT WORKS

  Step 1 — Image capture
    A physical device (camera/Raspberry Pi/IoT device) sends a POST request to:
      POST /classrooms/{classId}/image
    with a JPEG or PNG image as multipart form data. The request also includes
    a deviceId field which must match the classroom's registered deviceId —
    this ensures only the authorised device for that room can update it.

  Step 2 — Image decoding
    The backend reads the raw bytes and decodes the image with OpenCV
    (cv2.imdecode). If decoding fails the request is rejected with a 400 error.

  Step 3 — YOLO inference
    The YOLOv8 nano model (yolov8n.pt) is loaded lazily on the first request
    and cached in app.state.yolo_model for all subsequent requests. Running it
    on every request would add a multi-second startup cost each time.

    Inference is run in a thread pool executor (asyncio.run_in_executor) so it
    does not block the FastAPI event loop during the CPU-heavy inference.

    Call parameters:
      model.predict(img, imgsz=1920, conf=0.25, iou=0.45, augment=True)

    - imgsz=1920: processes the image at up to 1920px — higher accuracy for
      distant or small people
    - conf=0.25: detection confidence threshold — boxes below 25% confidence
      are discarded
    - iou=0.45: IoU threshold for non-maximum suppression — removes duplicate
      boxes for the same person
    - augment=True: test-time augmentation — runs inference on flipped/scaled
      versions of the image and merges results for better accuracy

  Step 4 — Person counting
    YOLO returns bounding boxes, each with a class index. Class 0 in the COCO
    dataset is "person". The backend counts how many boxes have class == 0.

    Occupancy is capped at the room's capacity:
      occupancy = min(person_count, classroom.capacity)

    This prevents the displayed occupancy from exceeding the physical maximum
    even if YOLO detects more boxes than seats (e.g. overlapping detections).

  Step 5 — Annotation
    The backend draws two lines of text onto the image:
      - "Occupancy: {count}/{capacity}"
      - Current timestamp in Lagos time (Africa/Lagos timezone)
    Color: light blue (234, 241, 246 in BGR). The annotated frame is then
    JPEG-encoded back to bytes.

  Step 6 — Cloudinary upload
    The annotated image is uploaded to Cloudinary under the folder
    "smart_classrooms/". The old image URL is replaced in the database.
    The previous image is deleted from Cloudinary at the same time to avoid
    accumulating orphaned files.

  Step 7 — Database update
    The classroom document is updated with:
      occupancy: new_count
      latestImage: new_cloudinary_url
      updated_at: now

  Step 8 — WebSocket broadcast
    The backend sends a "classroom_image_update" event over WebSocket to all
    connected frontend clients. The event payload includes the full updated
    classroom document. Every browser viewing the Dashboard immediately sees
    the new occupancy number and the new annotated image without refreshing.

PERFORMANCE
  The endpoint returns timing metrics for every request:
    decode_ms           Image decode time (typically 15–30ms)
    inference_ms        YOLO inference time (typically 200–500ms)
    face_recognition_ms FR pipeline time (800–1500ms, only when session active)
    cloudinary_ms       Upload time (300–600ms)
    db_ms               MongoDB write time (10–50ms)
    ws_broadcast_ms     WebSocket broadcast (5–20ms)
    total_ms            End-to-end total


================================================================================
  6. THE ATTENDANCE TRACKING SYSTEM (FACE RECOGNITION)
================================================================================

PURPOSE
  Automatically identify which enrolled students are present in a classroom
  during an active session, and mark their attendance without any manual input.

HOW IT WORKS — STUDENT REGISTRATION

  Before face recognition can identify a student, the student must register
  and upload their face photos. This happens through a public self-registration
  page linked to a specific course.

  Step 1 — Lecturer creates a course
    When a course is created, the backend automatically generates a UUID
    registrationToken and stores it. The lecturer copies the registration link:
      https://{frontend}/register/{token}

  Step 2 — Student visits the registration page
    The frontend resolves the token:
      GET /register/{token}
    and retrieves the course name to display on the page.

  Step 3 — Consent
    The student is presented with three mandatory consent checkboxes:
      1. Biometric consent — I understand photos will be used to create a
         facial recognition template.
      2. Manual alternative acknowledgment — I understand manual attendance
         is available and not consenting carries no academic penalty.
      3. Age declaration — I confirm I am 18+ or have parental consent.
    All three must be checked. The backend validates this server-side —
    the frontend check alone is not trusted.

  Step 4 — Photo upload
    The student uploads 1 to 5 clear front-facing photos. Different angles
    and lighting conditions improve recognition accuracy. The frontend allows
    drag-and-drop and shows previews of all uploaded images.

  Step 5 — Embedding extraction (backend)
    POST /courses/{courseCode}/register (multipart form)

    For each photo:
      a. The image bytes are loaded using face_recognition.load_image_file()
         which uses PIL internally and always produces an RGB numpy array.
      b. face_recognition.face_encodings(rgb) is called, which:
         - Detects the face location using dlib's HOG face detector
         - Runs the 68-point facial landmark predictor
         - Passes the face chip through dlib's ResNet face encoder
         - Returns a 128-dimensional float vector (the face embedding)
      c. If no face is detected in a photo, a 422 error is returned telling
         the student which photo failed.
      d. The embedding vector is added to the student's embeddings list.

  DATA MINIMISATION (NDPA s.24):
    The uploaded photos are NEVER written to disk.
    The uploaded photos are NEVER uploaded to Cloudinary.
    Only the 128-float embedding vectors are stored in MongoDB.
    The image bytes are discarded immediately after encoding.
    This means a student's face cannot be reconstructed from stored data.

  Step 6 — Student document creation
    The backend creates (or updates) a student document in MongoDB with:
      - Full name and matric number
      - The list of embedding vectors (one per photo)
      - All three consent flags set to True
      - Consent timestamp and version
    An Enrollment record linking the student to the course is also created.

HOW IT WORKS — SESSION AND ATTENDANCE

  Step 1 — Lecturer starts a session
    POST /sessions
    Body: { courseCode, classId }

    The backend checks that no other session is currently active for that
    classroom (one classroom, one active session at a time). A new Session
    document is created with status "active". A "session_started" WebSocket
    event is broadcast to all connected clients.

  Step 2 — Device streams images
    The same POST /classrooms/{classId}/image endpoint that handles YOLO
    occupancy also triggers face recognition. After YOLO counts people, the
    backend checks:
      database.get_active_session_by_classId(classId)

    If no active session exists → face recognition is skipped entirely.
    If an active session exists → face recognition pipeline runs.

  Step 3 — Face detection in the live frame
    The current frame (already decoded as a numpy array) is passed to:
      face_recognition.face_locations(rgb)
    This detects the bounding boxes of all faces in the image.

  Step 4 — Embedding extraction from the frame
    face_recognition.face_encodings(rgb, known_face_locations=locs)
    This extracts a 128-float embedding for each detected face in the frame.

  Step 5 — Comparison against enrolled students
    The backend fetches all enrolled students for the active session's course
    from MongoDB, filtering out any student where embeddingsDeleted == True
    (students who withdrew consent are excluded automatically).

    For each face detected in the current frame:
      For each enrolled student:
        distances = face_recognition.face_distance(
            student.embeddings,  # list of up to 5 reference vectors
            detected_embedding   # current frame embedding
        )
        best_distance = min(distances)

      THRESHOLD CHECK: if best_distance < 0.55:
        → Student identified as present
        → database.mark_attendance(sessionId, matricNumber, method="auto")

    The threshold 0.55 was chosen through testing. A lower threshold (e.g.
    0.4) would reduce false positives but miss more genuine matches. A higher
    threshold (e.g. 0.7) accepts more matches but risks false identifications.
    0.55 is a balanced default for controlled classroom environments.

  Step 6 — Mark attendance (idempotent)
    The mark_attendance database function is designed to be safe to call
    multiple times for the same student in the same session:
      - If the student already has an attendance record that was NOT manually
        overridden: update the markedAt timestamp (refresh the detection time).
      - If the student has a manually overridden record: do nothing. The
        lecturer's manual decision is final and face recognition cannot undo it.
      - If the student has no record yet: insert a new AttendanceEntry.
    This means even if the camera sends images every few seconds, the same
    student is not marked multiple times — they are simply re-confirmed.

  Step 7 — Broadcast attendance update
    If any new students were marked in this frame, a "attendance_update"
    WebSocket event is broadcast to all connected clients. The payload includes
    the updated session state and the list of newly marked matric numbers. The
    lecturer's browser updates the attendance list in real-time.

  Step 8 — Manual override
    PUT /sessions/{sessionId}/attendance/{matricNumber}
    Body: { status: "present" | "absent" }

    A lecturer can manually set any student as present or absent at any time
    during or after a session:
      - Sets manuallyOverridden: True on the attendance entry
      - If status is "present": upserts the entry with method="manual"
      - If status is "absent": removes the entry from the attendees array
        (absent is represented by absence, not a flag)
      - Once manually overridden, face recognition will never modify that
        student's record for the rest of the session

  Step 9 — End session
    POST /sessions/{sessionId}/end

    Sets status: "ended" and endedAt: now. Once ended, face recognition on
    subsequent images will no longer mark attendance for this session. The
    attendance record is frozen.

CONSENT WITHDRAWAL (NDPA s.36 — Right to Erasure)
  DELETE /courses/{courseCode}/students/biometrics
  Body: { matricNumber }

  Execution:
    - Sets embeddings: [] (clears all stored vectors)
    - Sets embeddingsDeleted: True
    - Sets consentWithdrawnAt: now()
    - The student document is NOT deleted — only biometric data is erased
    - All past attendance records are preserved
    - Future face recognition queries skip this student entirely
    - The student portal will still show their full attendance history


================================================================================
  7. HOW OCCUPANCY AND ATTENDANCE ARE CONNECTED
================================================================================

They share one endpoint, one physical device, and one classroom.

  Single image endpoint:
    POST /classrooms/{classId}/image

    This single endpoint does both jobs from the same image in one request:
      1. Run YOLO → count people → update occupancy
      2. Check for active session → if found, run face recognition → mark attendance

  Shared classroom context:
    Both systems are anchored to a classId. When a camera device sends an
    image, it identifies itself by classId and deviceId. The YOLO result
    updates that classroom's occupancy. The face recognition check looks for
    an active session with that same classId. The two systems do not know about
    each other — they both independently read and write through the classroom
    as a shared anchor.

  One does NOT require the other:
    - Occupancy updates run always, regardless of whether there is an active
      session. A classroom can track occupancy 24/7 with no courses configured.
    - Attendance tracking only runs when a session is active. If no session is
      active, face recognition is completely skipped (no compute wasted).

  They share the same real-time channel:
    Both the occupancy update and the attendance update are broadcast over the
    same WebSocket connection. The frontend listens for two events:
      "classroom_image_update"  → update occupancy + latest image in Dashboard
      "attendance_update"       → update attendance list in CourseDetail page

  Practical classroom flow:
    1. Camera continuously sends images (e.g. every 10-30 seconds)
    2. Dashboard always shows live headcount (occupancy from YOLO)
    3. Before class: lecturer starts a session via the Attendance page
    4. During class: same camera images now also trigger face recognition
    5. Students are marked present automatically as they are detected
    6. Lecturer can monitor the attendance list updating in real-time
    7. After class: lecturer ends the session
    8. Occupancy continues updating; attendance is now frozen


================================================================================
  8. FRONTEND ARCHITECTURE
================================================================================

API CLIENT (src/lib/api.ts)
  All HTTP calls go through a single centralized api object. No component
  calls fetch directly. This means the base URL, error handling, and data
  transformation are defined in one place.

  Error handling (throwOnError):
    FastAPI returns validation errors as an array of objects under "detail".
    A plain new Error(array) would produce "[object Object]". throwOnError
    parses the response body and extracts human-readable messages from both
    string and array detail formats.

  Transform functions:
    Raw MongoDB documents use snake_case or unusual field names. Transform
    functions (transformCourse, transformSession, etc.) normalize them into
    typed TypeScript interfaces that the frontend works with.

AUTH CONTEXT (src/contexts/AuthContext.tsx)
  Real server-side authentication (all four phases of auth_design.txt — see
  AUTH_CHANGES.md for the full change log). A student or staff member logs in
  with their UNILAG email and a one-time code sent by mail
  (POST /auth/request-code, POST /auth/verify-code); the backend issues a
  JWT, stored in localStorage and sent as an Authorization: Bearer header on
  every request. AuthContext exposes { token, user, loading, isAdmin,
  loginWithToken, logout, refreshUser }. The user object is never trusted from
  a cache — it is re-fetched from GET /auth/me on every mount.

  The legacy VITE_ADMIN_PASSWORD path has been fully removed — admin access
  is now only ever granted through the same email/code login as every other
  role, via ADMIN_EMAILS. isAdmin is simply user?.role === "admin".

  Role is never trusted from the JWT claim on the backend — auth.py's
  get_current_user dependency re-reads the role from MongoDB on every
  request, so a promotion, suspension, or role change by an admin takes
  effect immediately rather than waiting for the token to expire.

WEBSOCKET HOOK (src/hooks/useClassroomWebSocket.ts)
  Manages the WebSocket connection lifecycle:
    - Auto-connects on mount
    - Sends the JWT as the connection's first message
      (JSON.stringify({ token })) — the backend closes any connection that
      hasn't authenticated within 5 seconds, since browsers cannot set
      headers on a WebSocket handshake
    - Sends a ping message every 25 seconds to keep the connection alive
      (prevents proxy/load balancer idle timeout disconnects)
    - On disconnect: reconnects with exponential backoff starting at 1 second,
      doubling each time up to a maximum of 30 seconds — the token is re-sent
      as the first message on every reconnect
    - Cleans up on component unmount

ROUTING (src/App.tsx)
  Public routes (no auth required):
    /                     Home page + legacy admin-password login (see
                          KNOWN LIMITATIONS below — kept as a temporary
                          developer testing fallback, not yet removed)
    /login                Real email + one-time-code login

  Requires being logged in as any active (non-pending) role — redirects to
  /login?redirect=<path> if logged out (returning here after verifying), or
  to /pending-approval if the account has no role assigned yet:
    /dashboard             Classroom overview (was public before the auth
                           work — GET /classrooms now requires login)
    /classroom/:classId    Classroom detail
    /attendance            Course + session management
    /attendance/course/:courseId   Course detail

  Requires being logged in as a student specifically
  (ProtectedRoute allowedRoles={["student"]}) — same redirect-and-return
  behaviour. Both were public/unauthenticated before the auth work's final

================================================================================
  10. NDPA COMPLIANCE
================================================================================

The Nigeria Data Protection Act 2023 compliance is built into the system at
the data layer, not bolted on as an afterthought.

  s.24 — Data minimisation
    Uploaded registration photos are processed in memory only. They are never
    written to disk, never stored in the database, and never uploaded to
    Cloudinary. Only the 128-float embedding vectors extracted from the photos
    are stored. A face cannot be reconstructed from an embedding vector — the
    process is mathematically one-way.

  s.31 — Age requirement
    The registration form requires the student to explicitly confirm they are
    18 or older, or have parental/guardian consent. This is validated server-
    side — the backend returns a 422 if ageConsent is not "true".

  s.34 — Rights of a data subject (including access)
    The student portal (GET /students/lookup/{matricNumber}) returns the
    student's complete attendance history, consent timestamp, consent version,
    biometric active status, and consent withdrawal date if applicable. Any
    student can access all data held about them using only their matric number
    today; Phase 4 of the auth work changes this to read the matric number
    from the logged-in student's own token instead, with an explicit matric
    parameter accepted only for administrators.

    The email address collected by the auth work (see section 8) is personal
    data under the Act and falls under this same right of access — it should
    appear alongside the existing consent and attendance fields in any s.34
    response, and in the registration privacy notice.

  s.34 — Right to erasure, with s.35 — Withdrawal of consent
    DELETE /courses/{courseCode}/students/biometrics
    Instantly clears the embeddings array and sets embeddingsDeleted: True.
    Future face recognition queries filter out this student. The student record
    and all attendance history are preserved (non-biometric data). The consent
    withdrawal timestamp is stored for the audit trail.

    This endpoint is exercised as a withdrawal of consent under s.35, which
    triggers erasure of the data that was processed on that consent basis;
    erasure itself sits under s.34. (Previously cited here as s.36 — s.36 is
    the right to object, which is not what this endpoint does. Verify the
    exact subsection numbering against the gazetted NDPA text before relying
    on any of these citations in submission material.)

  Manual alternative
    The system never makes biometric consent compulsory. Every registration
    page explicitly states that a manual attendance alternative is available
    and that not consenting carries no academic penalty. The manualAltConsent
    checkbox confirms the student understood this — and is required for
    registration to proceed, ensuring the student has genuinely read it.

    - dlib compiles from source during pip install using the system gcc/g++
    - No pre-built wheel needed — compilation is automatic
    - No numpy version concerns — dlib is compiled against whatever numpy
      pip installs, so they always match

  Local Windows development:
    - Python 3.11 required (not 3.14 — dlib has no 3.14 wheel)
    - dlib installed via pre-built wheel (dlib-19.24.1-cp311-cp311-win_amd64)
    - NumPy must be < 2.0 (numpy 1.26.4) — the pre-built dlib wheel was
      compiled against numpy 1.x; numpy 2.x changes the C API and breaks it
    - See api_test_review.txt for the full explanation and fix

  Serve:   any static file server or CDN
  Dev:     npm run dev → Vite dev server on port 8080
  Env:     frontend/.env (VITE_* variables baked into the build at build time)

================================================================================
  12. KNOWN LIMITATIONS & NOTES
================================================================================

- Server-side authentication exists (JWT, role- and ownership-checked on the
  backend — see section 8/9 and AUTH_CHANGES.md) and is enforced on every
  endpoint, including registration and the student attendance lookup as of
  the auth work's final phase. The legacy client-side admin password
  (VITE_ADMIN_PASSWORD) still works in parallel, deliberately — kept as the
  developer's own temporary testing fallback until the mailer service (which
  actually delivers login codes by email) is confirmed working. See
  AUTH_CHANGES.md's Phase 4 section for the four places this touches and
  what to remove once it's no longer needed.

- The camera image endpoint (POST /classrooms/{classId}/image) has no secret
  or credential beyond the pre-existing deviceId comparison, which is
  discoverable from the public classrooms API. A shared-secret header for
  this endpoint was built, verified, and then reverted — hardware/firmware is
  outside the current maintainer's control and needs a decision with whoever
  owns the ESP32 firmware before this is attempted again.

- face_recognition and dlib are not imported at module level in main.py. The
  server starts and runs normally without them — only the registration and
  image capture endpoints will fail at runtime if they are not installed. This
  allows the backend to run in "occupancy-only" mode on lightweight deployments.

- The student portal (GET /students/lookup/{matricNumber}) returns 404 if the
  student has no ended sessions yet. Students who are registered but have had
  no sessions will see a not-found error rather than an empty results page.

- YOLOv8 nano (yolov8n.pt) is the smallest and fastest YOLO variant. It trades
  some accuracy for speed. For environments with poor lighting or many people,
  yolov8s.pt (small) or yolov8m.pt (medium) would detect more accurately at
  the cost of higher inference time.

- The face recognition matching threshold is hardcoded at 0.55. This works
  well in controlled classroom settings. Environments with varied lighting or
  students who look similar may benefit from tuning this value.

- Duplicate enrollment returns HTTP 409 Conflict (not 400). This is the correct
  semantic — 409 means "state conflict with the current resource state."
